# AI Loan Adjudication: Final Report

## Business problem

The task is to turn a loan-application dialogue into a decision and a clear customer explanation. The difficult part is not producing an answer. It is producing the same correct answer every time, using the active lending rules, while showing exactly why the decision was made.

The business opportunity is therefore a system that handles natural conversation cheaply, applies policy consistently, and sends only uncertain cases to a person. The same architecture can support new clients without training a separate model for every policy. Their rules can be loaded as configuration, evaluated deterministically, and retained in an audit record.

## Approach

The solution uses a small fine-tuned language model and a deterministic rules engine:

```text
Customer dialogue
      ↓
Qwen3-1.7B LoRA
Extract ten application fields and produce a shadow result
      ↓
Schema and completeness validation
      ↓
Deterministic rules engine
Recalculate the decision and failed rule IDs
      ↓
Verified customer explanation and audit record
```

The language model handles the part that benefits from language understanding: recognizing values in informal, out-of-order, corrected, or imperfect dialogue. It returns a fixed JSON structure containing ten application fields, a shadow decision, failed rule IDs, and a short explanation.

The model's decision is not authoritative. The rules engine evaluates every active JSON rule again. Rejection takes priority over review, review takes priority over approval, and missing information produces `COLLECTING_INFORMATION`.

The shadow result provides a monitoring signal. Invalid JSON, missing fields, conflicting evidence, or disagreement can be routed to human review.

## Why deterministic control is necessary in lending

Credit decisions have a higher explanation burden than a typical chatbot response. The U.S. Consumer Financial Protection Bureau states that adverse-action notices must give specific principal reasons, and those reasons must accurately describe the factors actually considered. Using a complex algorithm does not remove that obligation. [CFPB Circular 2022-03](https://www.consumerfinance.gov/compliance/circulars/circular-2022-03-adverse-action-notification-requirements-in-connection-with-credit-decisions-based-on-complex-algorithms/)

An LLM can produce a convincing sentence while citing the wrong threshold or omitting a failed rule. The deterministic layer ties the final decision and explanation to the rules actually evaluated. It can reproduce the same result for the same application and policy version, show which values and rules were used, and update a client's policy without retraining the model. This supports customer disputes, internal review, and audit preparation while reducing manual verification.

Deterministic execution does not by itself prove fair-lending compliance. The policy, input data, protected-class handling, and outcomes still require legal, compliance, and fairness review. Its value is narrower but important: the deployed system cannot silently substitute the model's invented policy or explanation for the approved rules.

## Why Qwen3-1.7B instead of a 14B serving model

This is a narrow structured task. The model does not need to memorize lending policy because the rules arrive with each application and the deterministic layer applies them again. Qwen3-1.7B can normalize the dialogue and produce coherent JSON with less GPU memory and compute than a 14B model. This should lower inference cost and latency, although both still need production benchmarks.

A 14B model may improve difficult language interpretation, but it costs more per application and still cannot guarantee correct rules or citations. A 14B model was tested for synthetic dialogue generation, but manual review found semantic field mismatches, so those candidates were rejected. The final dataset used reviewed field-specific templates and deterministic labels.

LoRA was chosen because it trains only a small adapter rather than updating the full base model. The final adapter is about 84 MB, which is easier to store, version, and replace. Policy changes remain in the rules file, not in a new policy-specific adapter.

## Data and training

The supplied material contained rules but no application dialogues, so synthetic data creation was the first implementation step. The dataset covers complete decisions, missing values, numerical boundaries, categorical aliases, corrections, contradictions, ambiguity, irrelevant text, and typos.

The core dataset contains 4,000 training, 500 validation, and 500 clean test records. Two additional training-excluded sets contain 500 records each: Test-2 for adversarial and messy dialogue, and Test-3 for unseen rule changes. Canonical values, decisions, failed rule IDs, and explanations were calculated by code rather than generated by an LLM.

Qwen3-1.7B was trained with QLoRA for two epochs, completing 250 steps. The [adapter](https://huggingface.co/sabber/snh-qwen3-1.7b-loan-adjudication-lora) and all [6,000 dataset records](https://huggingface.co/datasets/sabber/snh-loan-adjudication-synthetic) are published on Hugging Face.

## Results

All results below come from generation mode, where the fine-tuned model produced its JSON rather than receiving the expected answer.

| Evaluation set | Purpose | Model accuracy | Deterministic accuracy | Model citation exact | Deterministic citation exact |
|---|---|---:|---:|---:|---:|
| Validation | In-distribution model selection | 99.4% | 99.4% | 97.2% | 100.0% |
| Test-1 | Clean unseen applications | 99.4% | 100.0% | 95.8% | 100.0% |
| Test-2 | Adversarial and messy dialogue | 87.8% | 88.8% | 91.8% | 95.6% |
| Test-3 | Changed thresholds, actions and rule IDs | 78.6% | 91.6% | 53.0% | 75.4% |

Test-1 shows that the small model learned the normal structured task well. The deterministic layer corrected all remaining clean-set decision and citation errors.

Test-2 exposes the harder production risk. Prompt injection and irrelevant sensitive disclosures were handled well, but vague or contradictory answers sometimes became confident field values. The rules engine cannot repair a wrong value that looks valid.

Test-3 demonstrates the value of keeping policy outside the model. Under unseen policy changes, deterministic recomputation raised accuracy from 78.6% to 91.6% and reduced false approvals of expected rejections from 19 to zero. Remaining errors came mainly from extraction, showing that future training should separate extraction from policy interpretation more strongly.

Validation contained three incomplete applications that both layers approved because the model invented plausible missing values. Every extracted value therefore needs dialogue evidence, and unresolved evidence must force collection or human review.

## Business conclusion

The experiment supports a hybrid product rather than an end-to-end autonomous LLM. A 1.7B model keeps the language layer small and potentially inexpensive. Deterministic policy execution removes the cost and latency of a second verification model, lets a client update rules without retraining, and creates reproducible decisions and explanations. Those properties can reduce routine manual review while giving compliance and operations teams a result they can inspect.

The system is not ready to make unsupervised real-world credit decisions. The data is synthetic, so these results measure fidelity to the supplied rules and generated dialogue scenarios, not borrower risk or regulatory approval. Before a production pilot, the system needs evidence grounding, stronger contradiction detection, versioned audit logs, real-data evaluation, latency and cost benchmarks, and human review for missing information, model-engine disagreement, or configured review outcomes.

Within that boundary, the prototype offers low-cost language understanding, independently changeable policy, and verified customer explanations.
